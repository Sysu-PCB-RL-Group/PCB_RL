## 二、根因定位过程（要点回溯）

### 1. 一度误判为"元件密度过高"（已放弃）
- 原认为 Button（密度 67.9%）、Connector（45.2%）学不动是"密度太高，几乎无合法排布"。
- **用户关键纠正**：我给的板子都是**专家手工完美布局**，一定有解；不该筛选/跳过任何板。

### 2. 最终根因：环境的 valid_area 定义与专家"贴边布局"不兼容
- Button 的 U1 在原始文件里是**贴边放的**（Y 贴板框 96.03~108.03）。
- 但环境 `valid_area` 默认**内缩 BOARD_MARGIN=1.0**：板框高 12mm → valid_area 高仅 10mm。
- 网格取整：`expected_h = int(11.35 / 1.0) = 11` 格 > `grid_height = int(10/1.0) = 10` 格。
- **结果**：U1 放不进 valid_area → mask 全屏蔽 → reward 恒负 → 学不动。
- **结论**：不是板子没解，是**环境把专家能贴边放下的元件逼到无解**。

### 3. Connector 是独立问题（未在本次修改）
- 8 个可动元件**全部同层(TOP) + 全部 pkg_type=4**，间距阈值取 **2.0mm**。
- 填充率约 91%，几乎无合法排布 → 学不动。
- 与 Button（尺寸放不下）不同，需单独决策（调间距阈值/允许分层/降级）。

## 三、解决方案（已实施）

### 修复：取消 valid_area 内缩，BOARD_MARGIN 1.0 → 0.0

| 文件 | 修改 |
|---|---|
| `env/pcb_layout_env.py` | `Config.BOARD_MARGIN: 1.0 → 0.0` |
| `config/argument.txt` | `BOARD_MARGIN = 0.0` |

**原理**：`valid_area = (min_x+MARGIN, min_y+MARGIN, max_x-MARGIN, max_y-MARGIN)`。MARGIN 内缩 1mm + 网格取整，把 U1（需 11 格）挤出只有 10 格的区域。MARGIN=0 后 grid 高度 12 ≥ 11，U1 能放下。

**实测各板可放置性**（仅 Button 受影响，其余全 OK，且全部 grid ≤100 安全）：

| 板子 | 最大元件需格(h) | 板框h | MARGIN=1.0(旧) | MARGIN=0.0(新) |
|---|---|---|---|---|
| **Button** | 11 | 12.0 | **NO** ❌ | **OK** ✅ |
| Connector | 4 | 15.7 | OK | OK |
| 灯板2 | 4 | 12.2 | OK | OK |
| 按键侧板 | 1 | 18.0 | OK | OK |
| 开关小板 | 1 | 9.2 | OK | OK |

## 九、Root Cause：专家 reward 与 RL 环境 reward 标准冲突（reward 冲突假说）（2026-08-22）

### 1. 用户的关键质疑
> "专家轨迹本身是用放好的板子做的，照理说不应该就是好的吗？为什么还有不适合专家轨迹的板子？这有没有可能是 reward 标准和专家轨迹冲突导致的？"

### 2. 确凿证据：两套 reward 标准不一致
`env/expert_trajectory.py` 第 476-484 行 docstring 自述：
> "专家示范是'应该被模仿的正确行为'，**不携带惩罚项**。即使真实布局与环境阈值存在偏差，也不以负 reward 惩罚示范，**否则 Phase 2 TD 学习会被'照专家做回报为负'的坏信号带偏**。"

当前 `config/argument.txt`：`EXPERT_APPLY_PENALTIES = 0` → **专家 reward 只算品质奖励，不含惩罚**。

| | 专家轨迹 reward | RL 环境实时 reward |
|---|---|---|
| 品质奖励（Net聚合/拥塞/去耦/大元件） | ✅ | ✅ |
| 硬重叠惩罚 W_OVERLAP_HARD=20 | ❌ | ✅ |
| 软间距惩罚 W_OVERLAP_SOFT=10 | ❌ | ✅ |
| 出界惩罚 W_OUT_OF_BOUNDS=20 | ❌ | ✅ |
| reward clip [-30, +60] | ❌ | ✅ |

### 3. 冲突如何伤害训练
- **BC 预训练**：模型学"照专家动作走 → 拿纯正品质 reward"。
- **Phase 2 RL**：接真实环境 reward，突然混入惩罚项。同一个动作，专家标准里 +10，RL 标准里因贴边/间距变成 -20。
- **同一行为两套标准给相反信号 → 学习互相抵消 → 收敛不稳**。
- **Button 最严重**：U1 贴边放，专家标准里高正分，RL 标准里触发边界/间距惩罚变负 → with_expert 被先验拉向贴边又被环境罚 → 两难。baseline 无此先验，自由探索到不贴边布局反而学得好。

## 十一、概念澄清：专家轨迹"正确性" vs "reward 数值口径"（给组员对齐用）

**核心**："专家轨迹本身是对的（不加惩罚）" 与 "专家 reward 数值要与 RL 环境一致（加惩罚）" 是两回事。

| 层面 | 说明 | 是否应加惩罚 |
|---|---|---|
| **动作层**（专家做了什么） | 放置序列/位置，本就是完美布局，永远是对的 | 不需要（位置不违规，惩罚公式算出来本来就是 0） |
| **reward 数值层**（RL 给该动作打多少分） | 影响 DQN 学习目标 | 应**与 RL 环境同口径**（带惩罚） |

**为什么加惩罚不会冤枉专家**：专家完美布局的重叠/出界惩罚本来就是 0，带惩罚公式不会给专家扣冤枉分；只保证万一变异导致轻微贴边/超阈值，专家 reward 与 RL 环境给的分一致，两路信号不打架。

**组员观点的正误**：
- ✅ 对：专家轨迹的**动作/位置**是对的，不该被当违规示范惩罚。
- ⚠️ 混淆：他们说的"专家轨迹不加惩罚"是**动作层**；实验 D 说的是**reward 数值口径要与 RL 一致**，不是改专家轨迹，而是改计算专家 reward 的公式口径。

**一句话**：加惩罚不是在"怀疑专家轨迹不对"，而是在"让 RL 学习的尺子和环境的尺子对齐"。

### 4. 概念澄清：简单板 vs 复杂板，专家价值不同（回应"简单板专家意义不大？"）

**核心**：不是"专家对简单板没用"，而是"简单板上专家没有**增量**价值"。

| 板型 | 状态空间 | 专家价值 | 说明 |
|---|---|---|---|
| **简单板**(Button, 2元件) | 极小 | 无增量（不必要） | 纯随机探索就能学会（baseline 转正）；专家示范给的信息模型自己探索也能得到，不会让训练更好 |
| **复杂板**(灯板2 6元件, Connector 8元件) | 大 | 有显著增量 | 纯探索难撞到好布局；专家示范提供"先验方向"，加速收敛、提升质量 |

**专家示范的本质是"引导探索"，不是"提供答案"**：简单板不需要引导，复杂板需要。

**注意**：这不意味着要"筛掉简单板"。大规模训练混合复杂+简单板没问题——简单板靠探索学会、复杂板靠专家引导，各司其职。专家轨迹对每块板都提供正确示范，只是简单板上边际贡献小。

## 十四、复杂板对比实验：如何输入指令

## 十五、灯板2 实验：复杂板实测 + "专家锚定"根因（2026-08-22）

> 修正第十四节的假设：实测发现**即使复杂板（灯板2, 6 元件）with_expert 也不如 baseline**，问题不在"简单 vs 复杂"，而在**专家注入强度过大导致锚定**。

### 1. 第一轮：默认注入强度（BC_EPOCHS=50, RATIO=0.2）

| 指标 | with_expert | baseline |
|---|---|---|
| last_avg_r | **+36.8** | **+99.7** ✅ |
| last_avg_placed | 5.73/6 | 5.95/6 |
| 末段200 mean | +21.0（**停滞**） | +100.8 |
| 末段500 负值比例 | 35% | 10% |
| head mean | +34.3 | +40.2 |

**关键观察**：with_expert 的 head(+34)→tail(+21) **几乎不涨甚至略降**，被专家先验"钉死"在次优解附近；baseline 从 +40 稳步涨到 +100。→ 推翻了"复杂板专家有价值"的假设。

### 2. 根因：专家注入强度过大 → "锚定"

`run.py` 的 with_expert 两阶段机制产生两个"锚点"：
1. **BC 预训练 50 epoch**：把网络权重训练成"模仿专家"，可能**过拟合专家分布**，锁死初始权重。
2. **Phase 2 常驻 20% 专家经验**（RATIO=0.2）：在线训练时 20% 采样来自专家固定轨迹，**持续把策略拉回专家先验**，占用探索预算。

结果：with_expert 被锚定在专家示范附近，收敛上限被锁死。

### 3. 修复（方向 A）：降低注入强度

改 `config/argument.txt`：
```
EXPERT_BC_EPOCHS    : 50 → 10    # 减弱 BC 过拟合，只给"大致方向"初值
EXPERT_BUFFER_RATIO : 0.2 → 0.05 # 大幅降低专家常驻占比，探索主导
```
（专家轨迹本身没变，只需改注入强度，不需要重新生成专家轨迹。）

### 4. 第二轮：降注入强度后（BC_EPOCHS=10, RATIO=0.05）

| 指标 | 第一轮(默认) | 第二轮(降强度) | baseline |
|---|---|---|---|
| last_avg_r | +36.8 | **+55.2** | +99.7 |
| best_reward | 159.16 | **160.23** | 158.56 |
| 末段200 mean | +21.0 | **+80.95** | +100.82 |
| 末段200 负值比例 | 73/200 | **29/200** | 18/200 |
| head→tail | +34→+21(停滞) | **+39→+81(上升)** | +40→+101 |

**结果**：方向 A **确认有效**——with_expert 从"停滞"（head→tail 不涨）变为"持续上升"（+39→+81），last_avg_r +36.8→+55.2，末段负值比例大幅下降。

### 5. 最终结论与定位

- **"专家锚定"是 with_expert 收敛差的重要原因**，方向 A 已验证。
- **但 with_expert 仍差 baseline 约 20 分**（末段 +81 vs +101）——不必强求 with_expert 超过 baseline。
- **重新定位专家注入的价值**：专家提供的是"**高起点 + 保持可学习性**"（with_expert head +39 高于 baseline +34），而非"压过纯探索"。在大规模混合训练中，"高起点 + 不锁死"正是理想组合。
- **可选进一步调参**：`EXPERT_BC_EPOCHS` 再降到 5、或 `EXPERT_BUFFER_RATIO` 降到 0.02，边际收益可能递减。

### 6. 遗留
- Connector 的间距过严问题仍待单独处理（调阈值 / 分层 / 降级）。
- 本次改动的两个参数（`EXPERT_BC_EPOCHS=10`、`EXPERT_BUFFER_RATIO=0.05`）已作为新默认保留在 `config/argument.txt`，如需回退改回即可。

## 十六、Connector 单板验证（实验 A）——"reward 口径修复 ≠ 修复 Connector"（2026-08-22）

> 前提确认：本实验**是在修复 `EXPERT_APPLY_PENALTIES=1` + 重新生成专家轨迹（带惩罚口径）之后**跑的，数据可信。
> - 专家轨迹重新生成：`data/expert_transitions/`（8/22 19:58）
> - with_expert 训练：`result/experiments/A/...Connector.../with_expert/`（8/22 20:13）
> - baseline 训练：`result/experiments/A/...Connector.../baseline/`（8/22 20:31）
> - `config/argument.txt` 确认 `EXPERT_APPLY_PENALTIES = 1` 已生效。

### 1. 结果对比：reward 口径统一后，Connector 依然"专家未胜出"

| 指标 | with_expert | baseline | 谁优 |
|---|---|---|---|
| best_reward | 157.26 | **164.96** | baseline |
| 前 20% 均值 | -148.48 | -150.75 | 接近 |
| 后 20% 均值 | **-138.58** | -140.57 | with_expert 略好 |
| 最佳 placed | 8/8 | 8/8 | 平 |
| 训练轮 | 6500 | 6500 | 平 |

**结论**：即便统一了 reward 口径（专家轨迹也带惩罚，与 RL 同标准），Connector 的 with_expert 仍然没有反超 baseline。**这直接证实了 reward 冲突假说对 Connector 不成立**——Connector 的问题不是 reward 口径，而是独立的"间距约束过严/布局极难探索"。

### 2. 关键信号：reward 呈"两极分化"

两条训练曲线的 reward 都是：
- **大量 episode 在 -150 ~ -180**：placed 只有 3~6 个元件，随后触发 `EARLY_STOP_THRESHOLD = -150.0` 提前终止。
- **偶尔爆出 +20 ~ +160**：placed = 8/8，找到合法完整布局。

这说明：**该板存在合法完整布局（能拿高分），但极难找到**。多数时候模型只放 3~6 个元件就撞上间距/重叠惩罚，累计 reward 跌破 -150 被 early-stop。

### 3. 决定性几何分析：解法依赖"跨层堆叠"，探索极难发现

**板面与元件**：
- 板框：x[139.976,154.222]（宽 14.25mm）× y[94.327,110.073]（高 15.75mm）= **224 mm²**。
- 8 个可动元件**全部 package_type=4（CONN）**，同层任意两两间距需 **2.0mm**。
- 元件总面积 ≈ **109 mm² ≈ 板面积的 49%**，且元件尺寸大（4×4、4×4.65）。

**关键发现（读 best_layout 得出）**：with_expert 的最佳布局里：
- `JP2`（layer0）的 bbox 与 `Pad_e2`（layer1）的 bbox **完全一致**（x[140.976,144.976]×[96.327,100.327]）；
- `JP1`（layer0）与 `Pad_e5`（layer1）在 x-y 上**几乎完全重合**。

而环境对**不同层的元件允许 2D 投影重叠**（间距检查只在同层进行）。所以**唯一能把 8 个大元件塞进 224mm² 并满足 2mm 间距的办法，就是把元件"垂直堆叠"到对侧层上**——利用双层的 z 分离来节省 XY 空间。

**问题本质**：
- 不是"无解"，**是有解，但解法要求"跨层精确堆叠"**。
- 这种非平凡技巧**随机探索几乎不可能撞出来** → 绝大多数 episode 只能平铺放 3~6 个，随后撞上间距惩罚 early-stop。
- reward 因此**极度稀疏**（只有完整堆叠布局才给高分），RL 难以学到。

### 4. 结论与定位

1. **`EXPERT_APPLY_PENALTIES=1` 修复已经解决了 reward 口径冲突（Button/灯板2/开关小板方向）**，但对 Connector **无效**——它的困难不在此层。
2. Connector 的根因是**布局可行空间极小 + 解法要求跨层堆叠 + reward 稀疏**，是独立问题。
3. 与第十五节遗留一致，Connector 需单独决策，可选方向：
   - **A. 放宽间距**：把 CONN 的 2.0mm 间距阈值降下来（如 0.8/1.0mm），降低平铺难度，看能否不靠堆叠就放下。
   - **B. 显式分层引导**：reward 里给"跨层堆叠/双面利用率"一个显式奖励，把"堆叠"这个必要技巧变成可学习的先验。
   - **C. 降级 / 接受现状**：Connector 是极端困难板（49% 填充率 + 全同层 CONN），可暂时接受其 best~157（已能 8/8 完整布局），先推进其他板与跨板实验。
4. **方法论结论（回应"单板 vs 跨板"）**：本次验证回答的是"reward 口径修复是否让专家注入生效"这一**局部正确性**问题，用单板（实验 A + `--board Connector`）即足以定论，不需要跨板——跨板会引入板间干扰，反而无法归因。**单板验证在此场景下不仅够用，而且用对了**。

## 十七、方案 A 实施：放宽 CONN/通用 IC 间距阈值 + 修复"死配置"（2026-08-23）

> 针对第十六节结论（Connector 根因是间距 2.0 过严、只能跨层堆叠），实施方案 A：降低通用 IC/连接器间距阈值。

### 1. 关键发现：argument.txt 里的间距配置键原本是"死配置"

排查中发现：`config/argument.txt` 里的 `SPACING_CHIP / SPACING_SOIC / SPACING_QFP / SPACING_BGA / SPACING_IC / DEFAULT_SPACING` 在**任何 Python 代码中都没有被读取**（`search_content` 全库 0 命中）。

真正的阈值是**硬编码**在 `env/pcb_layout_env.py` 的 `spacing_threshold_for` 里：
```python
thresholds = [0.2, 1.2, 2.4, 5.0, 2.0]
```
也就是说，**即使有人改 argument.txt 里的 `SPACING_IC`，也不会生效**——这是历史遗留的"死配置" bug。

### 2. 具体修改

| 文件 | 修改 |
|---|---|
| `env/pcb_layout_env.py` | ① Config 新增 6 个属性：`SPACING_CHIP/SOIC/QFP/BGA/IC/DEFAULT_SPACING`，其中 `SPACING_IC` 默认 **1.0**（原 2.0）。② `spacing_threshold_for` 改为读取这些类属性（替代硬编码字面量），使 argument.txt 注入真正生效。 |
| `config/argument.txt` | `SPACING_IC = 2.0 → 1.0`（方案 A 的核心改动，放宽通用 IC/连接器间距）。 |
| `tests/test_env.py` | 修复 `test_config_spacing_threshold`：原测试硬编码 `[0.2,1.25,2.5,5.0,2.0]` 与代码从不对齐（旧代码也是 1.2/2.4），改为读取 Config 属性，与实现一致。 |

### 3. 间距类型映射（package_type → 阈值键）

| type | 含义 | 键 | 原值 | 新值 |
|---|---|---|---|---|
| 0 | Chip（片式） | `SPACING_CHIP` | 0.2 | 0.2 |
| 1 | SOIC/SOT/QFN | `SPACING_SOIC` | 1.2 | 1.2 |
| 2 | QFP 类 | `SPACING_QFP` | 2.4 | 2.4 |
| 3 | BGA/阵列 | `SPACING_BGA` | 5.0 | 5.0 |
| 4 | 通用 IC / 连接器 | `SPACING_IC` | **2.0** | **1.0** |

### 4. 预期效果

- Connector 板 8 个元件全部是 type4（通用 IC/连接器），间距要求从 **2.0 降到 1.0**，平铺可行空间显著增大，reward 不再极度稀疏。
- **无需重新生成专家轨迹**（间距阈值是 reward/约束层，专家布局坐标本身不变；但训练时 reward 计算会按新阈值走）。
- **需重新训练**才生效（奖励口径变了）。

### 5. 影响面提示

- 间距阈值是**全局生效**的（所有板、所有 type4 元件），不只是 Connector。对含大量连接器的板，平铺难度都会下降，属预期。
- 若担心 1.0 过松，可微调回 1.2~1.5；如需恢复原样，把 `SPACING_IC` 改回 2.0 即可（现在是真正可注入的了）。

1. `run()` 第 134 行打印 `Config.GRID_W` 时，**env 尚未实例化**，`load_dims_from_file` 未被调用 → 打印的是**代码默认值 21**。
2. 第 145 行 `_create_env()` 实例化 env → `PCBLayoutEnv.__init__` 无条件从 `config/admin.txt` 加载 → **`Config.GRID_W/H` 被改成 100**（类属性全局残留）。
3. agent 创建在 env 预加载**之后** → 用 `Config.GRID_W` = **100**。

**运行时验证**：
```
code default GRID_W/H = 21 21      ← with_expert 日志打印到的值
after admin.txt  GRID_W/H = 100 100 ← 实际训练用的值（agent 创建时）
```
**结论**：两次训练 GRID 实际都是 **100**，一致，无需修复对比逻辑。

**暴露的代码隐患（值得后续修，不影响本次）**：`run.py` 在 env 实例化前（134 行）打印 GRID_W/H 用的是未加载 admin.txt 的默认值，**日志具有误导性**；若某处依赖 `Config.GRID_W` 在 env 实例化前做决策，会用到错误的 21。建议后续把 `load_dims_from_file` 提前到 `Runner.__init__` 或修正打印时机。

- **未解决的瓶颈**：即使间距放宽到 1.0，reward 依旧稀疏，**模型无法稳定复现 8 元件布局**（最终 5 轮仍含 -172/-177 这类失败，后 20% placed 仅 5.8/8）。

**一句话**：方案 A 把 Connector 从"baseline 靠运气拿高分"变成"专家模型更稳定收敛"，稳定性指标首次明确反超；但根本瓶颈已转向 **reward 稀疏 / 探索效率**（"能找到解 best 166+ 但无法稳定复现"），下一步应聚焦于此。

### 3. 可选方向（聚焦 reward 稀疏 / 探索效率）

1. **奖励 shaping**：给"每一步合法放置更多元件"递增奖励，降低稀疏性，让模型逐步逼近 8 元件（思路详见对话）。
2. **调整 ε 探索 / warmup**：当前 ε 从 0.6 衰减到 0.137，后期几乎纯 greedy，可能过早放弃探索。
3. **跑更长轮数**：6500 RL 轮对困难板可能不够，best 在 ep6000+ 仍爬升。
4. **稳定放满 8 元件的"梯度"奖励**：对放置成功数进行子目标奖励，而非只给终点奖励。

## 二十、方案 1（reward shaping）实施：缓解 Connector 的稀疏奖励（2026-08-23/24）

> 针对第十八/十九节结论"reward 稀疏 → 探索效率不足"实施的方案 1：给"接近放满"递增奖励 + "放满 8 个"一次性大 bonus。

### 1. 关键代码证据：原实现"放满 8 个"没有额外奖励

`env/pcb_layout_env.py` 完成奖励分支原实现：
```python
completion_partial = W_COMPLETION / N_movable   # 200/8 = 25，每放一个 +25
if 放满 N 个:
    completion_bonus = W_COMPLETION - completion_partial * N_movable
                       # = 200 - 25*8 = 0  ← 放满 8 个没有额外奖励！
```
**含义**："放满 8 个"这个最终目标与"放第 1 个"奖励相同，模型无强烈动机坚持放满，多数 episode 停在 5~6 个。

### 2. 具体修改（`env/pcb_layout_env.py`）

**新增两个可配置权重（Config）**：
```python
W_SHAPE_STEP = 75.0        # 每放一个元件、随"已放数量占比"递增的 shaping 奖励上限
W_COMPLETION_BONUS = 100.0 # 放满全部 N 个时的一次性大 bonus
```

**重写完成奖励分支**：
```python
current_step = len(self.placed_list) + 1                 # 当前第几个（1-based）
completion_partial = W_COMPLETION / N_movable            # 基础 +25
shape_step = (current_step / N_movable) * W_SHAPE_STEP   # 递增 shaping，0→75
reward += completion_partial + shape_step
if current_step == N_movable:
    reward += W_COMPLETION_BONUS                          # 放满额外 +100
```

**效果**：第 1 个 +25，第 4 个 +37.5，第 8 个 +100（shaping 拉满）再 +100（放满 bonus），给"接近完成"一条平滑上升梯度。

### 3. 验证结果（7000/7500 轮，shaping 生效，GRID=21）

| 指标 | 改前(7000轮) | **改后(7500轮)** | 提升 |
|---|---|---|---|
| best_reward | 170.60 | **421.21** | **翻倍** |
| 前20% avg reward | -134 | **+66.7** | 负转正 |
| 前20% placed | 6.41 | **7.45** | 逼近 8/8 |
| 后20% placed | 5.80 | **6.76** | ↑ |

**结论**：方案 1 方向明确正确——best 翻倍、平均 reward 转正、placed 逼近 8/8。

> ⚠️ **方法论提醒**：改 reward 口径后，**跨版本只能看 placed，不能直接比 reward 绝对值**（量级已整体抬升）。

## 二十三、⭐ 专家轨迹 reward 尺度过小的发现（给 Connector 训练差提供新根因线索）（2026-08-24）

> 为回答"为什么专家轨迹效果总是不如不加"，直接检查了 `data/expert_transitions/*Connector*_expert.json` 的 reward 数值，发现一个**高度可疑的信号**。

### 1. 检查结果（Connector 800 条专家 transition）

```
顶层结构: list，800 条
reward: min=0.57  p10=4.20  p25=6.00  median=8.84  p75=15.13  p90=18.00  max=18.00
mean=10.32   ≤0 占比: 0.0%   正 reward 比例: 100%
```

### 2. 核心疑点：专家 reward 尺度与 RL 真实 reward 严重不匹配

| 量 | 值 | 说明 |
|---|---|---|
| 专家轨迹单步 reward | **0.57 ~ 18**（全正，中位 8.84） | 每条 transition 的 reward |
| `W_COMPLETION`（完成奖励） | **100** | 真实 RL 放满的奖励 |
| `REWARD_CLIP_MAX`（单步 clip 上限） | **60** | 真实 RL 单步上限 |

**专家轨迹里没有任何一条 reward 接近 60 或 100**，全部 ≤18。

**这意味着**：
- 专家轨迹的 reward **只包含"温和的品质奖励"（net 聚集/拥塞等，~+8 量级）**，**几乎不包含完成/放满的大奖励（+100）**；
- 而 RL 阶段模型自己探索到放满 8 元件，单步能拿 **+60（clip）甚至整局几百**；
- **两套 reward 尺度差 5~10 倍** → 专家 buffer 里的样本在 DQN 训练中表现为"低分样本"，反而像噪音，**拖累 Q 网络对高价值动作的估计**。

### 3. 与"专家轨迹不如不加"的直接关联

这提供了一条比"专家锚定"更本质的根因：**专家示范本身可能是对的（动作/位置），但它的 reward 数值尺度太小，在 DQN 里撑不起应有的引导权重**。当 `EXPERT_BUFFER_RATIO=0.2` 时，20% 采样来自这些"低分专家样本"，等于**稀释了在线探索的高分信号** → 这正是组员"专家轨迹研究很多方向都不如不加"的可能机制。

### 4. 待验证的方向（具体操作留待后续）

| 方法 | 验证内容 | 脚本/指令 |
|---|---|---|
| **A. 专家轨迹总 reward 统计** | 每条专家轨迹 8 步 reward 求和，看总分是否显著低于 RL best（400+）→ 实锤"专家轨迹本身 reward 就低" | 统计 `_expert.json` 按 `step_id` 分组求和 |
| **B. 纯 BC 推理** | 只用 `bc_pretrained.pt` 推理（不 RL 微调），看 placed/分数 → 判断专家轨迹本身质量 | 复用 `run_inference.py` |
| **C. reward 口径对齐** | 让专家 reward 也包含完成/放满奖励，与 RL 同尺度，再看 with_expert 是否改善 | 改 `expert_trajectory.py` reward 公式 + 重生成轨迹 |
| **D. 纯 RL 长训** | 直接关专家，纯 RL 训练更长，对比 best → 若纯 RL 更高更稳，专家即负优化，直接砍 | `--experiment A` baseline 长训 |

**问题①：所有专家轨迹都只有 5 步，不是完整布局步数**
- Connector 有 8 个可动元件，但每条专家轨迹仅 5 步 → **专家没有示范"放满所有元件"的完整流程**；
- Button / 按键侧板甚至只有 200 transitions（40×5）。

**问题②：reward 被 `REWARD_CLIP_MAX=60` 截断 → 全部顶格 60、毫无区分度**
- `_compute_expert_reward` 里 `apply_penalties` 默认 **False**（见 expert_trajectory.py:524 注释"专家示范不携带惩罚项"）；
- 结果：几乎所有专家轨迹的每步 reward 都 clip 到上限 60，整条轨迹总分恒定为 60；
- **DQN 从专家 buffer 采样时学到"每个动作都是 60 分"，无法区分动作好坏** → 专家样本不仅不引导，还把 Q 值拉平、稀释在线探索的高低分信号。

### 3. 直接解释"专家轨迹不如不加"

**不是专家动作错，而是专家 reward 全部一样（恒定 60）**。RL 阶段模型自己探索能拿到有区分度的 reward（放对 +60、放错被扣成负值），而专家 buffer 里全是"60 分平票"，采样越多越稀释真实信号。`EXPERT_BUFFER_RATIO` 越大，被稀释得越狠——这与历次"专家占比越高效果越差/不如不加"的观察完全吻合。

### 4. 修复方向（文档二十三节方法 C 的具体化）

| 修复项 | 当前 | 建议改法 | 位置 |
|---|---|---|---|
| ① 专家 reward 含惩罚项 | `apply_penalties=False` | 设为 `True`，让专家 reward 也有区分度 | `expert_trajectory.py` `_compute_expert_reward` / Config |
| ② 去掉/调高 reward clip | `REWARD_CLIP_MAX=60` 截断专家 reward | 专家轨迹单独不 clip（或调高） | Config / `_compute_expert_reward` |
| ③ 补全轨迹步数 | 5 步截断 | 生成到完整可动元件数（如 Connector 8 步） | `expert_trajectory.py` 轨迹生成逻辑 |

> ⚠️ 修复后需**重新生成专家轨迹**（`_regen_all_expert.py`）再训练。这是"专家引导"最值得先修的一环，优先于调 `EXPERT_BUFFER_RATIO`。
